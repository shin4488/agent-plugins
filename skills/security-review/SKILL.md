# 安全性を確認・改善する

入力元、権限を持つ処理、データの送信先・保存先をたどる。「誰のどの入力が、どの処理を通って、何を起こせるか」で問題を説明する。

## 調査する範囲

変更と関係する経路を選び、現在の実装・設定・公式仕様に基づいて判断する。

| 対象 | 判断の観点 |
| --- | --- |
| シェル・コード実行 | 外部入力が命令として解釈されないか。環境変数で受け、引用した引数で渡せるか |
| CIと本番権限 | 依存やリポジトリのコードを実行するビルドが、本番認証情報・OIDC権限に触れないか。検証した成果物と配布物が一致するか |
| 権限と信頼先 | 必要な主体・操作・対象に限定できているか。広い信頼設定や自己権限変更から制限を回避できないか |
| 通信 | 転送先への認証情報の漏れ、無制限の待機・応答サイズ、意図しない送信先がないか |
| 入力・ログ | 不完全・巨大・重複した入力や桁あふれをどう扱うか。応答・例外・ログに秘密情報が残らないか |
| 再試行 | 応答喪失や重複配信でも投稿・課金などが重複しないか。SDK・ジョブ基盤の再試行も含めて考える |

名称やアルゴリズム名だけで危険と断定せず、用途と契約を確認する。例えば外部プロトコルの署名方式を独自に変更すると、認証を壊す可能性がある。

## 改善と検証

- 起こり得る影響と根拠を示し、必要な範囲の対策を選ぶ。問題が確認できない箇所へ一律に仕組みを追加しない。
- 投稿・デプロイ・インフラ適用・権限変更は、コードの調査や修正とは別に実行範囲を確認する。
- 「秘密情報が送信・記録されない」「許可していない対象へ操作できない」など、対策後の結果を検証する。外部への副作用はフェイクや閉じた環境で置き換える。
- Action参照の固定は `pin-github-actions`、コミット対象の機密スキャンは `verify-changes` の手順を利用する。

確認できた経路、実施した改善、検証結果、実環境では未確認の点を報告する。リポジトリ固有の運用条件は、そのリポジトリの既存ドキュメントに残す。
