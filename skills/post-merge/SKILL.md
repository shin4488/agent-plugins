# マージ後の確認・本番反映・リリース

マージ後の依頼は、本番反映・本番確認・リリースまでを含む。リポジトリにその運用がない工程は行わず、その理由を記録する。

## 手順

1. GitHubで対象PRのマージ状態・取り込み先・マージコミットを確認する。ブランチが消えただけでマージ済みとは判断しない。
2. 作業ツリーと他のworktreeを確認する。残っている変更や他の作業を失わない状態で、取り込み先ブランチを更新する。

```bash
git fetch -p <remote>
git switch <取り込み先ブランチ>
git pull --ff-only <remote> <取り込み先ブランチ>
```

3. マージした変更が取り込まれたことを確認する。squash・rebaseでは作業ブランチのSHAがそのまま残るとは限らない。
4. 対象コミットに対応するCIを確認する。失敗していれば以降の工程へ進まない。
5. 本番へ反映する。`AGENTS.md`・デプロイ文書・リポジトリのskillから手順を確認する。自動デプロイならその結果を確認し、手動ならその手順で反映する。デプロイの仕組みがない、または配布物に影響しない変更なら不要と記録する。
6. 本番で、変更に関係する公開動作と配信内容を確認する。リポジトリの規約で禁止された確認は行わず、未確認の範囲として記録する。問題があれば以降の工程へ進まず報告する。
7. 本番確認で問題がなければ、`release` で前回リリース以降の差分をリリースする。他の変更とまとめてリリースする指示があれば保留し、未リリースの変更として報告する。既存のタグ・Release・リリース文書がないリポジトリでは行わない。
8. ローカル検証は `verify-changes` の結果を利用する。マージ時の競合解消・依存更新などで条件が変わった場合は、必要な範囲を再確認する。
9. 対象PRのブランチだけを整理する。進行中のPR・未公開コミット・他のworktreeから参照されていないか確認する。

```bash
git branch -d <作業ブランチ>
```

`-d` が拒否した場合は理由を確認する。squash済みでも拒否されることがあるため、未マージと断定せず、強制削除もしない。remote側は自動削除済みなら操作不要。

## 報告

取り込み先、CI、デプロイ・本番確認・リリースの結果（行わなかった工程はその理由）、削除したブランチ、残したものと理由を伝える。依存PRがある場合はbaseを再確認し、必要な変更を依頼の範囲で行う。
