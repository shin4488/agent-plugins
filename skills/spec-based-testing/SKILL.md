# 仕様に基づいてテストする

「何が守られるべきか」から確認項目を決める。期待値は、実装の写しではなく仕様・独立した計算・外部の契約から導く。

## 設計の観点

| 観点 | 考えること |
| --- | --- |
| 入出力 | 公開された入口から、必要な結果・失敗・外部への影響を確認できるか |
| 同値分割 | 同じ扱いになる入力をグループに分け、各グループの代表値を確認する。正常な入力だけでなく、不正な入力も分けて考える |
| 境界 | 空入力、境界の前後、重複、不完全なデータなど、仕様で結果が変わる条件は何か |
| 安定性 | 時刻・乱数・外部通信を制御できるか。実装方法を変えても同じ仕様を検証できるか |
| 独立性 | 期待値が本体と同じロジックに依存し、同じ間違いを見逃さないか |
| 読みやすさ | テスト名・入力・期待結果を読めば、どの条件でどう動く仕様か分かるように書く。失敗時に何が守られていないか判断できるか |

文字列の全文、例外型、ログ、呼び出し回数も、それ自体が外部仕様なら検証する。仕様でなければ、必要な内容・順序・件数など観測できる性質に絞る。

## 既存テストを見直すとき

- 振る舞いを変えていないのに壊れる理由を調べ、不要な内部構造への依存を減らす。
- 実データの複製や重複する確認を減らす。ただし、別の不具合を検出するテストまで一律に統合しない。
- 外部通信や投稿・課金は、固定入力やフェイクで置き換える。実サービスでの確認は別の必要性と実行範囲で判断する。
- テストのためだけに公開APIや層を増やす前に、既存の入口から検証できないか考える。

完成したテストが対象の不具合・仕様違反を検出できることを確認する。検証全体の実行と報告は `verify-changes` が担当する。
