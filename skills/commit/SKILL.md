# 変更をコミットする

一つのコミットが一つの目的を持ち、あとから内容を説明・取り消しできる単位にする。ファイル数や層ごとに機械的に分割する必要はない。

## 手順

1. リポジトリの開発ガイドと履歴から、ブランチ・メッセージ・署名の規約を確認する。
2. 今回の変更と、既存の無関係な変更を区別する。必要なら `create-branch` の手順を使う。
3. `verify-changes` で確認した差分・検証条件が、コミット対象と一致しているか確認する。同じ条件の検証は繰り返さない。
4. 必要なファイルまたは差分だけをステージし、`git diff --cached` で実際に入る内容を確認する。
5. コミットし、対象ファイル・メッセージ・作成者を確認する。

## メッセージと作成者

- メッセージの言語・prefixはリポジトリの規約に従う。規約がなければ、Conventional Commitsに従って、なぜその変更をおこなったのかを表す文にする。
- 公開リポジトリでは公開可能なGitの作成者情報を使う。個人メールをログへ表示せず、GitHubのnoreply設定などを確認する。
- AIエージェントが作成するコミットには、メッセージ末尾に `Co-Authored-By` を必ず付ける。実際に作業したエージェント名と、そのサービスの公開用noreplyアドレスを使う。
- エージェントやモデルが変わった場合は、その実行環境に合わせて表記を変える。別のAIの名前・アドレスを流用せず、確認できないモデル名やアドレスを推測しない。
- 複数行のメッセージはファイルに書き、`git commit -F <ファイル>` で渡す。

```text
fix: 不正な日付で処理が停止するのを防ぐ

Co-Authored-By: <実際のAIエージェント名> <そのサービスの公開用noreplyアドレス>
```

コミット後は、末尾の表記が欠けていないことと、今回使ったAIに一致することを確認する。

push・PR作成は依頼に含まれる場合に続ける。「コミットして」という依頼では、新しいコミットを作る。既存コミットの書き換えや、force-pushによるリモート履歴の上書きは、その操作をユーザーが明示的に依頼・承認している場合だけ行う。
