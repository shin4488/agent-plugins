# 変更を検証する

変更によって壊れ得る動作を特定し、それを確認できる方法を選ぶ。リポジトリの必須チェックを守り、変更と関係のない検査を一律に増やさない。

## 判断すること

| 観点 | 確認する内容 |
| --- | --- |
| 対象 | 作業ツリー・ステージ・コミットのどこまでが今回の変更か。生成物やローカル設定が混ざっていないか |
| 動作 | 変更が影響する入力・出力・依存関係。ビルド、lint、既存テスト、動作確認のうち何で確認できるか |
| 検証の実効性 | CIが対象を実行しているか。skip・pending・テスト未検出を成功と取り違えていないか |
| 機密情報 | コミット対象に認証情報・非公開の環境値・個人情報がないか |
| 関連文書 | コマンド・配置・設定・仕様の変更に対して、案内やリンクが古くなっていないか |

リポジトリの開発ガイド・CI・既存ツールから具体的な確認方法を選び、実行する。新しいテストが必要なら `spec-based-testing`、安全性の設計を調べる必要があれば `security-review` を参照する。

## 機密情報の扱い

- スキャン対象はコミットする内容に絞り、gitignoreされた秘密ファイルを含めない。既存のgitleaks・git-secretsなどを使い、独自の検出ルール集を増やさない。
- redactを有効にする。値を伏せないツールの出力は捕捉し、検出行をそのままチャットやPRへ出さない。
- 一致しただけで秘密とは判断しない。認証情報、公開済みの識別子、テスト用のダミーを区別し、リポジトリの規約で判断する。
- 実際の秘密が見つかったら公開を止める。公開済みなら無効化・再発行が必要なことを伝え、独断で履歴を書き換えない。

## 完了条件

- 選んだ検証が何を保証するか説明でき、実行結果が確認できている。
- 問題は修正し、直せないもの・未実施の範囲・理由を明示している。
- 機密情報と関連ドキュメントを確認し、必要な更新が済んでいる。

結果には対象の差分と条件を残す。同じ作業中の同じ差分・依存・設定・検証条件なら、コミットやPR作成のたびに再実行しない。条件が変わった場合だけ影響する確認を追加する。結果管理のための専用ファイルは作らず、チャットやPR本文を使う。このskill自体はコミット・push・PR作成を行わない。
