# わかりやすく書く

会話や経緯を知らない読み手が、短い時間で正しく理解できるように書く。文書・PRの本文・コードコメント・回答と報告に共通して使い、リポジトリに書き方の規約があればそれを優先する。

## 決まり

| 対象 | 決まり |
| --- | --- |
| 言葉 | 一般的な用語で書き、造語・比喩・定型的な言い回しを避ける。日本語の文章では「repo」と略さず「リポジトリ」と書く。文書の言語を保ち、日本語は日本人に、英語は英語圏の読者に自然に伝わる表現にする |
| 構成 | 図と表を説明の土台にし、文章は図と表で表せない前提と理由だけにする。図を増やすことが目的ではないため、流れ・関係・比較を文章より速く伝えられるときに使う。抽象的な説明には具体例を添える。同じ内容は1か所に書き、ほかからは参照する |
| 正しさ | 根拠のない事実を推測で書かない。確かめていないことは、確かめていないと書く |
| Markdownの書式 | 文の途中で改行しない（lint・formatが求める場合を除く）。表示先によって改行が空白や改行として表示され、文が途切れるため。参考リンクは本文の該当箇所に置く。コードブロックはコード・コマンド・出力にだけ使い、説明文を囲まない。太字の端が全角の括弧なら、`**` の外に半角空白を入れる。CommonMarkでは、全角の括弧と日本語の文字に挟まれた `**` が太字にならないため |
| コードコメント | コードから読み取れない意図・前提だけを書く。経緯・変わりやすい値・他の資料の場所など、変更のたびに古くなる内容は書かない |
| 回答と報告 | 質問には結論から答える。報告は、結果・確かめたこと・確かめていないことを分ける |

## 図と表の選び方

| 伝えたいこと | 使うもの |
| --- | --- |
| 処理や判断の流れ | 流れ図（mermaidの `flowchart`） |
| 複数の主体のやりとりと順序 | シーケンス図（`sequenceDiagram`） |
| 型・部品の構造と関係 | クラス図（`classDiagram`） |
| 状態と、その移り変わり | 状態遷移図（`stateDiagram-v2`） |
| 複数の項目を同じ観点で比べる | 表 |

mermaidのラベルに半角の括弧・記号・`<br>` を含めるときは、ラベルを `"` で囲む。

## 例

| 決まり | 避ける | 書く |
| --- | --- | --- |
| 一般的な用語 | 変更の前にガードレールを敷く | 変更の前に、出力を比べるテストを足す |
| 推測で書かない | このエラーはネットワークの問題です | 3回のうち2回、接続のタイムアウトで失敗した。原因は確かめていない |
| 太字と全角の括弧 | `必ず**（承認後に）**実行する` | `必ず **（承認後に）** 実行する` |
| コードコメント | `# 先月の障害を受けて追加した。詳細は運用手順書を参照` | `# 再試行しても二重に課金しないよう、送信IDで重複を除く` |
| 報告 | 対応しました。たぶん動きます | 結果: 失敗していたテストが通った。確かめたこと: 単体テストとlint。確かめていないこと: 本番のデータでの動作 |
