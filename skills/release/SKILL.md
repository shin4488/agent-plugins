# リリースを準備・公開する

以下の順で進め、完了済みの工程は確認して引き継ぐ。リポジトリ固有のコマンドは開発ガイドから案内されるリリース文書を使う。前提を満たさない場合は、依存する次の工程へ進まない。

## 1. リリース条件を確認する

リポジトリの `AGENTS.md` / `CLAUDE.md`、リリース文書、既存タグ・Releaseを確認する。

| 確認するもの | 確定する内容 |
| --- | --- |
| 依頼範囲 | 準備までか、タグ・Releaseの公開までか。デプロイ・ストア申請は誰が行うか |
| 版番号 | 増分の規約、タグ・Release名、変更するバージョンファイル |
| 対象 | リリース対象ブランチ、先にマージするPR |
| 成果物 | 必要なビルド・パッケージと、内容の検査方法 |
| 公開条件 | 先行デプロイ・API互換性・CI・人間の確認が必要か |

既存の依頼で確定している内容は再確認しない。版番号や公開条件が不足していれば、差分を調べて具体案を示し、必要な点を確認する。

## 2. バージョン変更と成果物を準備する

1. リポジトリの規約に従って版番号を更新する。自動生成されるファイルは規定のコマンドで更新する。
2. `verify-changes` で必要な検証を行う。公開用のビルド条件・接続先・権限・版番号が正しいか確認する。
3. 必要な成果物を作成して内容を確認する。配布対象外の設定や秘密情報を入れない。成果物のGit管理はリポジトリの規約に従う。
4. PRが必要なら `commit`・`create-pr` を使う。マージは既存の依頼・リポジトリの規約に従い、マージ待ちの間は対象タグを作成しない。

## 3. 公開対象のコミットを確定する

1. 必要なPRのマージを確認し、remoteとタグを取得する。
2. リリース対象ブランチのコミットSHAを記録する。以降の公開操作は動くブランチ名だけに頼らず、このSHAを指定する。
3. 検証結果・成果物がそのコミットに対応するか確認する。squashによるSHAの変化だけなら内容を照合し、コード・依存・ビルド条件が変わっていれば再ビルド・再検証する。
4. 同名タグ・Releaseが既にあれば、対象SHAと公開状態を照合する。一致する完了済み操作は繰り返さず、不一致なら止める。既存タグを削除・付け替えしない。

## 4. ノートと公開内容を確定する

前回の該当リリース以降の差分・マージ済みPRからノートを作る。言語・体裁は依頼とリポジトリの規約に合わせ、言語の指定がなければ英語で書く。変更点を箇条書きで簡潔にまとめ、タグ名・対象SHA・成果物・ノートを確認できる形にする。

公開が承認済みなら進める。承認が必要な場合は、準備と検証を済ませてから、この具体的な内容への承認を求める。

## 5. 公開して確認する

既存CIがタグ・Releaseを作成する場合は、その手順を使って結果を確認する。手動のGit・GitHub CLI操作で公開する場合は、次の順で進める。

1. タグが未作成なら、確定したコミットSHAを指すタグを作成してpushする。タグの形式はリポジトリの規約に従う。

```bash
git tag <タグ> <対象SHA>
git push <remote> refs/tags/<タグ>
```

2. タグが既にある場合は、参照先が対象SHAと一致することを確認して使う。ローカルにだけある場合は、そのタグをpushする。
3. リモート上のタグを確認してからGitHub Releaseを作成する。タグのpushでCIがReleaseを作る場合は、その完了を確認し、二重作成しない。

```bash
gh release create <タグ> --verify-tag --title <Release名> --notes-file <ノートファイル>
gh release view <タグ>
```

成果物が必要ならリポジトリの手順で添付する。公開後はタグの実際の参照先・Releaseの内容・添付ファイルを確認する。応答が不明な場合は状態を調べてから再実行する。

## 6. 結果を報告する

版番号、対象コミット、ReleaseのURL、成果物の場所を伝える。実機確認やストア申請など人間の作業が残る場合は、必要な手順と対象ファイルを示す。GitHub Release作成だけで、本番デプロイやストア公開まで完了したとは扱わない。
